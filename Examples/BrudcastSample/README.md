# Brudcast iOS sample

A small SwiftUI app built the way a customer's app would be, with each SDK call where a real app
puts it: identify at sign-in, reset at sign-out, a screen view as each screen appears, events as
the user shops, and message buttons that open the app's own screens. It also has the notification
service extension. It builds the SDK from this repository, so changes to `Sources/` show up on the
next run.

## Run it

1. Copy `Config/Local.xcconfig.example` to `Config/Local.xcconfig` and set
   `BRUDCAST_PUBLISHABLE_KEY` to the publishable key of an in-app application in the dashboard.
   `Local.xcconfig` is ignored by git.
2. Open `BrudcastSample.xcodeproj` and run the `BrudcastSample` scheme on a simulator.

To run on a device, also set `DEVELOPMENT_TEAM` and a `SAMPLE_BUNDLE_ID` your team can sign in
`Local.xcconfig`. The App Group `group.<SAMPLE_BUNDLE_ID>` is shared with the notification service
extension.

`BRUDCAST_ENVIRONMENT` picks `production`, `staging`, `uat`, `development` or `local`. `local`
talks to `brudcast-in-app-delivery-service` on this Mac at `BRUDCAST_LOCAL_PORT` (8191).

## Sign in like a real app

Set `SAMPLE_BACKEND_URL` in `Local.xcconfig` to a backend of your own, and the sign-in screen signs
users in through it: the backend computes the user hash with the identity secret, the app passes it
to `Brudcast.identify`, and **Send me a welcome** on Home has the backend send the user an in-app
message through the Brudcast API. The identity secret and the API key stay on the backend. Without
it, sign-in takes a pasted user hash instead.

The backend needs two endpoints, both taking and returning JSON:

| Endpoint | Body | Response |
| --- | --- | --- |
| `POST /login` | `{ "userId", "email" }` | `200` with `{ "externalId", "userHash", "email" }`, where `userHash` is `hex(HMAC-SHA256(identitySecret, externalId))` |
| `POST /welcome` | `{ "externalId" }` | `2xx` once it has sent the user an in-app message with `POST /in-app/messages` on the Brudcast API |

On an error, the app shows the response's `message`.

[brudcast-sample-backend](https://github.com/brudcast/brudcast-sample-backend) implements both in a
few short TypeScript files; run it locally to try the flow.

`CustomerFlowUITests` drives the whole app on a simulator: sign in, receive the welcome message and
tap its button, shop through to a placed order, find the action in the activity log, sign out. It
needs the stack and the backend running, so it is skipped unless the test runner gets
`BRUDCAST_E2E=1`:

```sh
TEST_RUNNER_BRUDCAST_E2E=1 xcodebuild test -project BrudcastSample.xcodeproj \
  -scheme BrudcastSample -destination 'platform=iOS Simulator,name=iPhone 15'
```

## Change the project

The Xcode project is generated by [XcodeGen](https://github.com/yonaskolb/XcodeGen) 2.46 from
`project.yml`. Edit `project.yml`, never the `.xcodeproj`, then regenerate and commit both:

```sh
brew install xcodegen
xcodegen generate
```

CI regenerates the project and fails when it differs from the committed one. Adding or removing a
source file in the `BrudcastSample` or `NotificationService` folder also needs a regenerate.

## The app

```
Sign in ──▶ Home ┬ Shop ──▶ Product ──▶ Checkout
                 └ Account ──▶ Sign out ──▶ Sign in
```

The sample keeps its own session in `UserDefaults`, as an app keeps its login, so a relaunch lands
on Home while the SDK restores its identity.

| Where | What the SDK does |
| --- | --- |
| Sign in | `Brudcast.identify` with the hash from the backend (`SampleSession.signIn`) |
| Every screen | `Brudcast.screen`: `SignIn`, `Home`, `Shop`, `Product`, `Checkout`, `Account` |
| Home | The inbox bell and its unread badge, and **Send me a welcome** through the backend |
| Product | Tracks `product_viewed` with `product` and `price` |
| Checkout | Tracks `checkout_started` with `product` and `total` on arrival, `order_completed` on **Place order** |
| Account | Notification permission, pausing and syncing messages, the activity log, developer tools for any event or screen, and sign-out with `Brudcast.reset` |

To try a campaign, trigger it with `checkout_started` or the `Checkout` screen and go to checkout.
Set a button's action to `brudcast-sample://checkout` or `brudcast-sample://shop` and tapping it
opens that screen: the action handler routes the sample's own links and records every action in
the activity log, and anything else uses the SDK's default behaviour.

## Push

Push sends through FCM, so the sample needs your Firebase project to receive notifications:

1. Add `https://github.com/firebase/firebase-ios-sdk` with the `FirebaseMessaging` product to the
   `BrudcastSample` target, and `GoogleService-Info.plist` to the `BrudcastSample` folder.
2. Configure Firebase at launch and pass its token to the SDK:

   ```swift
   FirebaseApp.configure()
   Messaging.messaging().delegate = self

   func messaging(_ messaging: Messaging, didReceiveRegistrationToken fcmToken: String?) {
       if let fcmToken { Brudcast.push.setToken(fcmToken) }
   }
   ```

3. Run on a device with push notifications enabled for your bundle id, and tap **Allow
   notifications** on Account.

The notification service extension attaches images and records deliveries through the App Group
without any Firebase code.
